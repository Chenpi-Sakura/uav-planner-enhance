### 口径换代带来的结论变化

| 用例 | 旧口径（平均风当湍流） | 新口径（脉动方差） |
| --- | --- | --- |
| 昌都-拉萨 2022-12-01 | **不可飞**，附 3 个替代起降点 + 2 个备选时段 | 可飞，06:00 起飞 |
| 拉萨-林芝 2022-12-01 | 高风险，15:00 起飞 | 中风险，07:00 起飞（3 h 网格下为 06:00） |
| 拉萨-日喀则 2022-12-01 | 中风险，05:00 起飞 | 低风险，09:00 起飞 |

冬季长途那条从"不可飞"变"可飞"正是本次修正要解决的误判：旧公式在强平均风（急流）下给出高 TKE，
把航路整个封死；新公式只看脉动方差，同一条线的沿途脉动量并不高。

矩阵因此不再覆盖不可飞分支，改由以下两处补：

- 端到端手工用例：昌都→拉萨 2022-02-05 08:00 → `不可飞 / reason = search_iteration_limit`
  （注意这不是"被封死"而是"没搜完"，弹窗文案按 reason 区分，见 `NoticeDialog.vue`）；
- 自动化：`tests/golden_plan.py` 的 `s_start_blocked` / `s_all_nan` 合成用例，
  以及 `tests/test_risk.py` 的四档边界断言。

接口耗时（新口径，本机暖读）：`/api/assess/feasibility` 1.1–3.0s、
`/api/assess/time-window` 1.2–1.8s（矩阵头两次含 ±6 h 窗口带来的冷读，各约 6.0s）、
`/api/route/plan` 0.3s（冷读首条约 6.4s）、`/api/weather/overlay` 0.6s。
窗口从"单帧"扩到"±6 h 共 13 帧"后取数量级未变，冷读多出的部分来自磁盘首次触碰新增帧。
（2026-09-24 的 3 h 复跑是在临时实例上、与常驻实例的启动预加载并发进行的，
头两条用例测到 5.2/8.4 s，属磁盘争用，不要当计时依据。）

本矩阵可随时复跑（需后端已启动）：

```powershell
cd backend
.python/portable/python.exe scripts/acceptance_m5.py
```

脚本会逐项校验「结论自洽 / 距离适用性 / 窗口输出项 / 时区口径」并打印 PASS-FAIL 汇总，最近一次运行 **6/6 PASS**。同一用例连续复跑 3 次结果完全一致（推荐起飞时刻、窗口与风险值不变），证明扫描是确定性的。
要在新起的实例上跑（不动本机常驻后端）：`$env:UAV_API_BASE="http://127.0.0.1:9091"` 后再执行。

## 4. M5 修复项：全平台时间基准统一

M2 已实测确认 NetCDF 时间标签为 UTC、UI 输入为北京时间（依据温度日变化相位对经度回归，
斜率 −0.0663 h/deg 与理论 −1/15 吻合），但当时只在时间窗口链路做了换算，
功能一与规划器仍直接把北京时间字符串当数据标签使用——这是计划书 §12 列出的头号风险。

M5 的处置：

1. 新增 `backend/timebase.py`，把换算收敛为单一实现（`to_data_time` / `to_user_time` /
   `to_data_time_str` / `to_user_time_str` / `data_timezone_meta`）；
2. `planner.py`、`feasibility.py`、`main.py`（profile / overlay）全部改为查表前换算；
3. `time_window.py` 删除重复实现，改为引用 `timebase`（保留同名别名，兼容既有测试）；
4. 新增 `backend/tests/test_timebase.py`（8 项），用替身 loader 断言规划器实际查询的是
   `2022-07-01T00:00` 而非 `2022-07-01T08:00`，并覆盖跨日边界与开关关闭两种情形。

修复后同航线（拉萨→林芝 2022-07-01 08:00）规划结果由 322.0 km 变为 312.3 km，
符合同一起飞时刻改取正确气象场后的预期差异，可飞性与风险等级结论不变。
