> 代码基线：`main` @ 230be8e（v1.0 的盘点基线；v1.1 只更新湍流阈值与两处与代码不符的描述）

## 1. 目标概述

在现有 4D 气象感知路径规划器之上，新增两个面向飞行决策的功能，并按会议决议在前端加入标签页切换与 AI 辅助评估：

- **功能一 · 飞行路径可行性评估**：对给定起降点输出**四态结论**（可飞 / 不可飞 / 超预算 / 未算出，见 §4.2.1），可飞时给出距离、时间、风险等级（全程 + 按城市分段）；否则给出原因、风险分布、绕行成本分析与建议措施。
- **功能二 · 飞行时间窗口规划**：在期望日期内寻找湍流最低且全程安全的时间窗口；当日无窗口时向前预测 7 天，输出推荐时刻、湍流曲线、备用时段与预警提示。

**决策口径（均已按会议纪要锁定）**：

1. 成本因素只考虑 **时间成本**（不引入经济成本模型）。
2. 算法沿用现有 **改良版动态 A* + 分块优化**，对外名称维持「A*」。
3. 数据精度局限（约 5km 空间分辨率）先接受，在 UI 中明确标注数据口径。
4. AI 评估定位为「把二元结论升级为带地名与气象依据的中文飞行建议」。

**本轮不做（明确出界）**：经济成本模型、多高度层（仍固定 500hPa）、多机调度、真实降水变量（数据集中无降水，用湿度做代理指标并注明）。

### 2.2 关键差距（本计划要补的）

1. **`planner.py` 失败时静默回退直线**——上层无法区分「真实安全路径」与「兜底直线」，可行性结论不可信。必须改造为返回 `found` / 失败原因。

5. 缺少**自然语言评估 + 地理信息关联**（AI 辅助评估，会议待办 #1）。
6. 前端只有单一规划表单：无标签页、无评估结果面板、无地图联动高亮（会议待办 #2）。

## 4. 功能一 · 可行性评估设计

### 4.1 输入（对应需求表 2.2）

| 参数 | 说明 |
| --- | --- |
| `start` / `end` | 起点终点经纬度（复用现有输入） |
| `waypoints` | 可选途经点 |
| `priority` | 任务档位：`urgent` 紧急 / `normal` 平衡 / `economy` 安全 → 同时决定 A\* 湍流软惩罚倍率与绕行成本阈值（2026-09-24 起进搜索，见 §4.4；JSON 键名沿用 `economy`，只有文案是「安全」） |
| `expected_window` | 期望飞行窗口（日期 + 起飞时段） |
| `speed` | 航速 km/h（默认 60） |
| `tke/edr_threshold` | 可选阈值覆盖（默认走 config） |

### 4.2 评估流程

```
1. 直线基线：d_straight、t_straight = d_straight / speed
2. 调用 planner.plan_path_ex(...) → (path, d_route, t_route, found, fail_reason)
3. 若 found：
   a. 沿路径逐点取（到达时刻, TKE, EDR）→ risk.profile() → 全程等级与统计
   b. 分段：按「重要城市间隔点」切段（geo.cities_on_path）→ 每段等级
   c. 绕行比 R = d_route / d_straight（同速下等价于时间比）
   d. R ≤ 优先级阈值 → 结论「可飞」；否则 → 结论「超预算」并保留路径供参考
   否则：按 planner 的失败原因分说「不可飞（无安全路径）」或「未算出（迭代上限）」
        → 前者再走 blockage.analyze() 给出阻塞原因
4. 生成建议措施（§4.5）
5. （可选）assessor 生成自然语言评估文本
```

#### 4.2.1 结论四态（2026-09-25 由两态扩来）

`feasible=False` 混着三类性质完全不同的事，全印成「不可飞」会把三档对比读反：
安全档的软惩罚是 ×4，代价函数逼它绕开一切中风险区，于是它比另外两档更容易撞上绕行预算
或迭代上限——「紧急=可飞、平衡=可飞、安全=不可飞」在旧口径下看起来像"越保守越危险"，
事实是"更安全的线存在，只是超预算 / 没来得及算出来"。

| verdict | 界面词 | 触发原因码 | 性质 | 配色 |
| --- | --- | --- | --- | --- |
| `feasible` | 可飞 | — | 有安全航线且在预算内 | 绿 |
| `infeasible` | 不可飞 | `no_safe_path` / `data_coverage_insufficient`（planner: `blocked` / `no_data`） | 走廊真被封死，或起降点查不到数据 | 红 |
| `over_budget` | 超预算 | `detour_exceeds_threshold` | **线存在**，只是绕行比超出该档 R_max | 黄 |
| `undetermined` | 未算出 | `search_iteration_limit`（planner: `iteration_limit`） | A\* 用完本次展开预算还没搜完，有没有线还不知道 | 灰 |

- 枚举、中文词与两张映射表都在 `backend/schemas.py`（`VERDICT_*` / `VERDICT_LABELS` /
  `PLANNER_REASON_VERDICT`），`feasibility.REASON_VERDICT` 与 `route_options.summarize_plan()`
  各取所需；响应里 `verdict`（机器码，前端选色/选图标）与 `conclusion`（同一个词的中文）并存。
- 功能二的 Top-K 候选行也吃这套：没有预算判定，所以只会出现 `infeasible` / `undetermined`，
  风险档那一格在未算出时显示「未算出」（灰）而不是「不可飞」（红）。
- **展开预算随航程伸缩**（`planner.expansion_budget`，系数与上下限在 `config.py`）：
  `max_iter = clamp(100 次/km × 该段直线距离, 20000, 120000)`。写死的旧值对长短两条线是
  两种强度——824 km 的线连搜索框（起终点外接矩形各放 `SEGMENT_PAD_DEG=2°`，0.045° 格）
  都有 3.6 万个格点，20000 次连一遍都扫不完。下限沿用旧值，这条只允许让长线多算。
  预算按**段**算（有途经点时每段各用自己的直线距离）。斜率 2026-09-26 由 60 重标为 100：
  绑定值是昌都→拉萨 604 km 安全档 40204 次（66.6 次/km）加五成余量。
- **预算的单位是"研究过的路口"，不是"堆弹出次数"**（2026-09-26）：A\* 现在带 closed set
  （`planner.py` 的 `settled_g`），同一节点被重复弹出的陈旧副本直接跳过、不计数。
  判据是"`g_score` 与上次展开时相同"而不是"已在集合里"，后者会误杀被改进后重新入队的节点。
  同一条 824 km 线的实测：三档展开数 24179/30077/37646 → 13662/15884/20065，
  而路径、里程、累计代价、`explored` 逐字节不变。来龙去脉见 `docs/backlog.md` B1 追加。
- **`search_effort = {expansions, budget}`**（2026-09-26）：`功能一`/`plan-multi`/`功能二` 三个
  响应都带，四态里 `undetermined` 的四处入口（卡片 tooltip、评估详情、失败弹窗、候选行）
  与 AI 报告统一显示「已研究 N 个路口 / 预算 M」。没跑到搜索时为 `null`，不报「0 / 0」。
  浏览器里能稳定复现的是前两处：后两处要三档同时顶格，实测那已接近 120 s 接口超时（见
  `docs/backlog.md` B1 追加之四）。
- **A\* 有墙钟上限，且预算与时间取先到者**（2026-09-26）：`ASTAR_TIME_LIMIT_S = 18` 管单次搜索
  （从开始展开计时，气象取数不计入；到点报 `time_limit`），`ASTAR_REQUEST_TIME_LIMIT_S = 30`
  管整次请求 —— 功能一的替代起降点扫描、功能一的三档并评、功能二的几何与 Top-K 共用同一份余额。
  起因是「未算出」那次点击要 35~56 s，而分段计时显示主搜索只占 3 s，贵的是赠品式的 26 次全程
  重规划。`time_limit` 与 `iteration_limit` 同属未算出，分开的是那句解释（到点不能说「用满预算」），
  `search_effort` 为此多带 `elapsed_s`。来龙去脉见 `docs/backlog.md` B1 追加之五。
- **量纲已统一（2026-09-26）**：A\* 的距离项、软惩罚与启发式都在**真实公里**上算。此前代价在
  度空间算（30°N 上一格是 5.00 km × 4.32 km 的长方形，却按正方形计价），东西向绕行被多收约 15%，
  软惩罚的「等效绕行公里」在横竖两个方向不是一个价。启发式相应从正方形 octile 换成长方形网格
  最短距离（`planner.heuristic`），直线偏离决胜项改作堆的次级键——并进 h 会顶破一致性，
  实测同一格点被重展开 12 次。代价函数的**形式**不变（距离 + 超阈部分线性加权）。
  四组对照与全过程见 `docs/backlog.md` B1 追加之三/之四；一致性由 `tests/test_astar_metric.py` 守住。

### 4.3 风险分级口径

与现有硬/软约束阈值对齐：

| 等级 | 判定（满足其一即取高等级） | 含义 |
| --- | --- | --- |
| 低风险 | TKE < 8 且 EDR < 0.208 | 安全 |
| 中风险 | 8 ≤ TKE < 16 或 0.208 ≤ EDR < 0.295 | 轻度颠簸，可飞需注意 |
| 高风险 | 16 ≤ TKE < 26 或 0.295 ≤ EDR < 0.376 | 强烈颠簸，谨慎 |
| 不可飞 | TKE ≥ 26 或 EDR ≥ 0.376 | 命中硬约束 |

> 单位：TKE 为 m²/s²，EDR 为 m^(2/3)/s。EDR 一列不是独立标定的，是同档 TKE 经
> `ε = 0.8·k^1.5 / L`（L=2000 m）、`EDR = ε^(1/3)` 换算而来，改任一边的阈值都必须同步另一边。
> 定档依据与三区抽样占比见 `docs/backlog.md` B5 落地记录。

辅助指标：`max_tke`、`max_edr`、中度以上格点占比、连续暴露最长距离（km）。
全程等级合成规则：任一点达到「不可飞」→ 不可飞；高风险占比与连续暴露超限 → 整体上调一级（规则在 `config.py` 可调）。

### 4.4 绕行成本（时间口径，对应会议决议）

- 绕行比 `R = 航线总距离 / 直线距离`（同航速下即时间比）
- 时间增量 `ΔT = (d_route - d_straight) / speed`
- 优先级阈值（建议默认值，config 可调）：

| 档位 | 软惩罚倍率 | 阈值 R_max | 含义 |
| --- | --- | --- | --- |
| 紧急 urgent | 0.25 | 1.25 | 只为逼近硬阈值的湍流绕行，最多接受 +25% 时间 |
| 平衡 normal | 1.0（基线） | 1.5 | 现行为，最多 +50% |
| 安全 economy | 4.0 | 2.0 | 宁可绕远也要压低中风险以上暴露，最多 +100% |

倍率乘在 `DETOUR_PENALTY_TKE_COEF / _EDR_COEF` 两个基线值上，**两项同倍缩放**：
`EDR = 0.0737·√k` 是同一个湍流量换了单位，分别调会连带改两者之间的相对权重。
倍率只进 A\* 的软惩罚，**硬阈值（TKE≥26 / EDR≥0.376 / NaN 禁区）三档共用**——
"能不能飞"不由产品档位决定。

`POST /api/route/plan-multi` 一次产出三档各一条航线（几何 + 里程 + 绕行比 + 风险统计），
前端叠图：选中档实线 100%，其余两档按各自档位色画 50% 虚线，线本身可点击切档。
沿程湍流都没越过中风险下沿（8 m²/s²）时惩罚不参与代价，三档必然同解，
响应以 `meta.all_identical = true` 如实标出，前端提示"三档算出的是同一条线"。
定标依据与实测数字见 `docs/backlog.md` B1 落地记录。

超阈时输出「绕行成本分析」：直线距离 / 航线距离 / 时间增量 / 所用阈值 / 超出比例，并附替代方案引用。

### 4.5 阻塞原因分析与建议措施

**阻塞分析（`blockage.py`）**

1. 危险掩膜 `M = (TKE ≥ 硬阈值) | (EDR ≥ 硬阈值)`，取期望窗口时刻。
2. `scipy.ndimage.label` 求连通域，保留与 A–B 直线走廊相交的连通域。
3. 特征提取：面积（km²）、形状（条带状 / 块状：PCA 主轴-短轴长宽比）、`max/mean TKE·EDR`、与直线最近距离。
4. 输出 top-3 阻塞区 → 地图高亮（圆心+半径 或 轮廓多边形）+ 文案（如「存在约 X km² 的块状高湍流区横亘于拉萨—日喀则之间」）。

## 5. 功能二 · 时间窗口规划设计

### 5.1 输入（对应需求表 3.2）

| 参数 | 说明 |
| --- | --- |
| `start` / `end` | 起降点经纬度 |
| `date` | 期望日期（默认沿用现有 `targetDate`） |
| `forecast_days` | 预测天数，默认 7（当日无窗口时向前扫描） |
| `speed` | 航速 km/h（决定飞行时长与到达时刻） |
| `scan_step_hours` | 扫描步长，默认 1h = 数据真实分辨率（2026-09-24 曾改 3h 后回退，见 §5.3 与 `docs/backlog.md` B2b） |

### 5.2 评估流程（「路径几何一次 + 时次批量」策略，B10 后为两遍）

为避免 24 时次 × 7 天反复跑 A*（性能不可接受），采用**物理信息法**：路径几何只算一次，时间只做推进与查表。

2026-09-25 起这件事分成两遍：**第一遍**照旧用一条走廊查表扫 24 个槽位（几十毫秒）；
**第二遍**只给进入 Top-K 的 ≤4 个候选各按其**自身起飞时刻**跑一次 A\*，并按真实航线重排推荐。
第二遍复用第一遍已读进内存的气象场（`planner.plan_path_ex(req, field=…)`），因此不再产生
NetCDF 读取——否则四个候选各读一份 31 帧的网格，一次时间窗口评估会从 1 s 拖到 3 s 以上。

```
1. 几何基线：优先使用功能一同参数的规划路径；若无安全路径，
   退回「直线路径离散化」（并按硬约束判断该时段是否本身被阻断）。
2. 沿路径等距采样（步长约 0.1°，与气象网格对齐），得到采样点列 P_i
   与累计距离 s_i；总时长 T = d_route / speed，则 t_i = t0 + (s_i/d_route)·T。
3. 对期望日期每个候选起飞时刻 t0 ∈ {00:00 … 23:00}（整数小时）：
   a. 批量查询各采样点在 t_i 时刻的 TKE/EDR → 沿路径 max/mean、硬约束命中情况；
   b. 判定「全程安全」：飞行期间全部采样点低于硬阈值（TKE<26 且 EDR<0.376）。
4. 窗口聚合：相邻的安全起飞时刻合并为连续时间窗口
   → 推荐窗口 = 全窗口内「路径最大风险」最低者；
   → 推荐起飞时刻 = 该窗口内风险最低的时刻（平局取较早）；
   → 备用时段 = 其余安全窗口（最多 3 个）。
4b. Top-K 细排（B10）：候选 = 推荐窗口 + 备用时段各取其窗口内最优槽位，
   不足 K 个时在推荐窗口内再均匀补起飞时刻（全天都安全时那些会并成一整个窗口）。
   每个候选按自身时刻规划真实航线，排序键为
   可飞 > 整体风险档 > 沿程最坏点 max TKE > 里程 > 起飞时刻；
   没得出可飞结论的候选照样返回（带 verdict / reason），不静默消失；
   「未算出」（搜索没收敛）在候选行里不得显示成「不可飞」，见 §4.2.1。
   注意「沿程最坏点」排在「里程」之前：走廊全天平静时四条线几何与里程全等，
   直接比起飞时刻会让冠军因时钟跳到半夜。
5. 湍流曲线（输出项）：评估域 = [t0−1h, t_landing+1h]，按 30min 步长，
   对每个时刻取路径全体采样点的 max TKE / max EDR / mean TKE（曲线三条，
   前端双 Y 轴展示）；标注推荐起飞、预计降落。
   曲线与预警跟着**细排冠军**走，不跟第一遍的走廊级结果。
6. 其他预警：风速（u/v 合成）、相对湿度（代理降水提示，如 RH>80% 提示
   可能降水、RH>90% 提示结冰/云中飞行风险）、低温提示（tc 阈值）。
7. 当日全部时刻不安全 → 不可飞分支：
   a. 各时段风险分析表：每小时一行（max TKE/EDR、等级、建议）；
   b. 逐日扫描 date+1 … date+7（复用 3–4 步，路径几何不变）；
   c. 最佳备选日期 = 7 天内首个满足安全窗口的日期；全无 → 输出 7 天
      风险趋势与「建议推迟任务并等待气象更新」。
8. 记录「不可飞行原因」：区分「全天无安全时段」「航路本身存在永久阻塞
   （地形/NaN 区）」「数据覆盖不足（起降点超出数据范围）」三类。
```

### 5.3 数据粒度说明（重要）

实测数据为 **2022 全年逐小时（8760 帧）**，优于会议记录的「3 小时一次」：

- 窗口扫描与曲线默认按 **1 小时步长**，可在 config 调整为 3 小时；
- 「预测 7 天」的数据口径 = 数据集内 2022 年日期范围（当前数据为历史切片，
  对外文案统一表述为「基于现有数据向前推演 7 天」，不宣称实时预报）；
- 起降点若超出数据经纬度范围（lat 303 格 / lon 543 格覆盖范围），
  返回「数据覆盖不足」而非误报不可飞。

### 6.1 定位与内容

会议决议：**把「可飞 / 不可飞」的二元结论升级为带地名、带气象依据的中文飞行建议**。
（2026-09-25 补充：二元结论本身也扩成了四态，见 §4.2.1 —— 报告里「不可飞」这个词
从此只对应"走廊被封死 / 查不到数据"，超预算与未算出各有各的字。）评估报告由以下段落构成（内容全部来源于结构化结果，不凭空生成）：

| 段落 | 素材来源 |

| 时间建议 | 功能二推荐窗口与备用时段、风险随时间变化规律（如「午后湍流显著增强」） |
| 操作建议 | 绕行成本、绕行建议（替代起降点/时刻）、注意事项清单 |
| 数据口径声明 | 5km 空间分辨率、逐小时时间分辨率、TKE/EDR 为代理估算的口径声明 |

### 6.2 数据流与防幻觉

```
feasibility/time_window 结构化 JSON
        ↓ assessor.build_context()
【规则模板版】jinja 风格字符串模板 → 中文报告文本（离线、确定性、可测试）
【LLM 版】上下文 JSON 嵌入 prompt → OpenAI 兼容接口（config 可配 base_url/model/key 环境变量）
        ↓
   报告文本 + 引用数据块（前端 ReportCard 展示，可复制/导出）
```

- LLM prompt 明确约束：只允许引用给定 JSON 中的数值与地名；不确定时使用「数据显示」措辞；禁止编造天气事实。
- LLM 调用失败/未配置时自动降级到规则模板版，保证演示可用性。

### 6.3 三种落地路线对比（需拍板）

| 路线 | 说明 | 工作量 | 依赖 | 适用 |
| --- | --- | --- | --- | --- |

- 三档卡片与结论卡的颜色一律跟 `verdict` 走（绿/红/黄/灰，§4.2.1）：黄色要说清
  "线存在、只是贵"，灰色要说清"没算完"，两者都不能用红色。

## 8. 性能与数据层设计

### 8.1 瓶颈分析

| 场景 | 现状 | 风险 | 对策 |
| --- | --- | --- | --- |
| 单次规划 | 局部 bbox 切片 + 矢量化查询 | 可接受 | 保持 |
| 功能二 · 24 时次 × 7 天 | 若每时次跑 A* → 不可接受 | 高 | 「路径几何一次 + 时次批量查表」策略（§5.2） |
| 批量查表 | NetCDF 逐点读取慢 | 中 | `data_loader` 新增 `get_turbulence_series(points, times)`：按天 slab 读取 + 内存缓存（LRU，键=日期+bbox） |
| overlay 反复渲染 | 每次请求重画 | 低 | 保持现状（演示级） |
| 长耗时请求 | FastAPI 单 worker | 中 | 继续 `run_in_executor`；评估接口预计 2–8s，接口层加超时保护 |

### 8.2 数据层新增能力（`data_loader.py`）

1. `get_turbulence_series(lats, lons, times)`：批量返回 (n×m) TKE/EDR 矩阵（n 采样点 × m 时次）。
2. 按天缓存：`_day_cache[(date, bbox_hash)] -> ndarray`，上限 4–6 天，供窗口扫描复用。
3. 数据覆盖检查：`check_coverage(lat, lon) -> bool`，用于「数据覆盖不足」判定。
