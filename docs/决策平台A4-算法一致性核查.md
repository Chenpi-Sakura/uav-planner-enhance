# A4 · 核心寻路算法一致性核查

> 版本：v1.0（2026-09-23）
> 起因：`docs/Meeting0922.md` —— "我问他算法有没有发生变化，他说没有……我怕他把核心的这个路线算法怎么改了"
> "没有，其实改了，告诉你，别改了。不知道无法判断。"
> 结论先行：**A\* 的代价函数与启发式零改动；改的是"失败时说什么"和"用哪个时刻的气象"。**
> 把时间对齐后，同一份数据上 9/11 用例的航线路径**逐比特一致**。

---

## 1. 核查方法

| 层次 | 做法 | 回答的问题 |
| --- | --- | --- |
| 静态 | `git diff 230be8e..main -- backend/planner.py` 按语义行分类 | 代价函数被动过没有 |
| 取数 | 抽出 `get_meteorology_grid` 函数体逐行比对 | 规划器吃进去的气象场变没变 |
| 动态 | 基线 `230be8e` 与 main 同数据 A/B 对跑，路径用 `repr()` 逐比特记录 | 真实 NetCDF 上输出是否相同 |
| 语义 | `backend/tests/golden_plan.py` 合成平局/降级用例连跑两次比对 | 时间轴并列、NaN、起点越限的判定是否稳定 |

基线代码取法（不放进工作树跟踪的路径，用后即删；脚本见 `scripts/ab_baseline.py`）：

```bash
mkdir -p .tmp-algo-audit-base
for f in config.py data_loader.py meteorology.py planner.py schemas.py; do
  git show 230be8e:backend/$f > .tmp-algo-audit-base/$f
```

必须放在**仓库根的直接子目录**里：`config.py` 用 `dirname(dirname(__file__))/data` 解析数据目录，

## 3. 取数：规划器读到的气象场完全相同

`get_meteorology_grid`（A\* 唯一的数据入口）函数体在两个版本间**逐行一致**——44 行原文相同，
main 只是在它**后面**新增了 `read_slab()` / `check_coverage()`（功能二用的批量读，走另一条路径，
不影响规划器）。

唯一的例外在出图侧：`get_overlay_image()` 里 `gaussian_filter(sigma=1.0)` 改成了 `sigma=0.0`
（覆盖层去掉了平滑）。它只影响**热力图观感**，不进搜索。若"看着像算法变了"来自地图颜色变硬，
根因在这条。

## 5. 那 2 例到底发生了什么

### r_qamdo_lhasa_winter：起点本身在危险区

main 新增的起点安全校验（`planner.py:243-255`）在这条上生效。实测该起点：

```
UI 输入 2022-12-01 08:00 → 数据标签 2022-12-01T00:00
起点 (31.15, 97.18) 该时刻：TKE = 1.5329（硬阈值 1.0）→ 不安全
该 25 帧窗口内第 2 帧（02:00）起，起点才回到 TKE = 0.936
```

基线**没有起点校验**，于是它照样从危险格点里长出一条 163 点的路径。这条路径在原版本里会被显示为
"规划成功"，但它的第一个节点就违反硬约束。

### r_tight_thresh：把阈值收到不可能有路

阈值 TKE 0.2 / EDR 0.05 下不存在安全路径。基线返回 2 个点——就是
`return [Point(start), Point(end)]` 那条兜底直线；main 返回 `found=False`。

真实用户看到的是这一列：同一个"08:00"，基线拿 08:00 查表，main 拿 00:00 查表（后者才对）。

| 用例 | 基线 230be8e | main |
| --- | --- | --- |

| r_lhasa_nyingchi | 70 点 / 311.71 km | 70 点 / 312.26 km |
| r_via_nym | 49 点 / 246.17 km | 49 点 / 236.46 km |
| r_dangxung_linzhou | 10 点 / 52.97 km | 10 点 / 53.07 km |

里程变化幅度 0.2%–4.9%，属"换了正确的气象场"；最后一行是**旧版本伪造航线、新版本判不可飞**的典型样本。

## 7. 里程口径变了（路径没变，数字变了）

同一批逐比特一致的路径上，两边总里程都不同。原因是统计方式换了：

- 基线：A\* 推进时按等距圆柱累加每一跳 `phys_dist`（`Δx·cosφ, Δy` × 111）。
  用同一公式重算它自己的路径，结果 `base/重算 = 1.00000`，即基线里程就是网格累计值；
- main：`plan_path_ex` 收尾时对路径逐段求 `_haversine_km`（`planner.py:466-475`），是真大圆长度。

同路径下 main 比基线大约 **+0.17%**（236.5152 → 236.9305）。这是**展示口径**变化，
不是搜索变化，但它会让"同一航线里程和以前不一样"被当成算法异常。

## 8. 合成用例：平局与降级语义稳定

`backend/tests/golden_plan.py --synth-only` 连跑两次，输出 JSON **逐字节一致**
（6 条：时间轴整点两侧平局各一正一反、恰好压整点、起点越限、全区 NaN、中度湍流软惩罚道路）。
其中"并列取更早一小时"这条语义最容易在把 `argmin` 换成 `searchsorted` 时被悄悄改掉，现由这两条用例锁死。

## 9. 变更清单（全部为有意，按影响排序）

| # | 变更 | 引入于 | 对结果的影响 | 性质 |
| --- | --- | --- | --- | --- |
| 1 | 删掉"搜不到返回直线"兜底，改为 `found` + `reason` | `0c374b9` | 原先"看似成功"的直线现在明确判不可飞 | **修正确性**，会议看到的"线消失/变短"主要是它 |
| 2 | 新增起点安全校验 | `0c374b9` | 起点越限立即 `blocked`，不再从危险区长出路 | 修正确性 |
| 3 | 时区统一（北京时间 → 数据标签 −8h） | `8feb6ef` | 同一 UI 输入改查正确时次，里程 0.2%–4.9% 变化 | 修正确性 |
| 4 | 日期/区域越界返回 `no_data` 而非 500 | `0c374b9`/`1ce6ef1` | 数据覆盖不足不再伪装成"被湍流封死" | 修正确性 |
