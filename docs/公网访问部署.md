# 公网访问部署（frp + OpenResty）

面向「气象数据留本机、只让他人访问服务」的部署形态。数据（六个 NetCDF 实测共 614 GB + SRTM）始终不上云，
过隧道的只有页面、热图 PNG 与 JSON 响应。

服务器 `117.72.38.57`，对外域名 `uav.caipiischenpi.top`（OpenResty 按二级域名反代，域名前面挂着 Cloudflare）。

| --- | --- |

## 拓扑

```
访问者浏览器
   │  https://uav.caipiischenpi.top     ← 访客→CF 这一段一定加密
   ▼
Cloudflare（代理模式，域名解析到 CF 的地址）
   │
   ▼
服务器 OpenResty:443 ──► 127.0.0.1:12002 ──frp 隧道──► 本机 127.0.0.1:9090  FastAPI
   ├─ 限流 / 热图 proxy_cache / SSE 关缓冲                      ├─ /        → frontend/dist
   └── frps:7000 ◄────────── 本机 frpc 主动连出 ───────────────┘─ /api/...  → 寻路 / 评估 / AI 报告

本机 5173  Vite dev server —— 只给自己用，永不转发
```

对公网只暴露 **443**（访问）与 **7000**（frp 控制）。**12002 与 7500 都是服务器内部端口，不放行。**
`serverAddr` 用裸 IP：frp 控制通道是直连 TCP，不经过 OpenResty，与域名解析、证书完全解耦。

经行 Cloudflare 有两个必须记住的后果：nginx 眼里的 `$remote_addr` 是 **CF 的出口 IP，不是访客的**
（限流键要用 `$http_cf_connecting_ip`，见 3.3），以及 CF→源站那一段是否加密取决于你选的加密模式
（建议 `Full (strict)`，否则源站 443 到 CF 之间是明文）。

> **不要把 Vite dev server 转发出去。** 两个独立原因：
> 1. dev 模式下 `server.fs.allow` 放行仓库根目录，任何人可用 `/@fs/G:/.../backend/planner.py`
>    原文读取源码，也能读到 `frp/frpc.toml` 里的 auth token——拿到 token 即可冒充你的客户端接管隧道。
>    （Vite 默认 `fs.deny` 只挡 `.env` / `.git` / `.DS_Store`。）
> 2. dev 首屏是数百个未压缩模块请求，全部经「本机上行 → 隧道 → 服务器出口」，公网打开十几秒起步。
>
> 另外 Vite 在本机只监听 `[::1]`（IPv6 回环），`frpc` 用 `127.0.0.1` 根本连不上它——这是同一件事的第三层提醒。

## 前置条件

| 项 | 要求 |
| --- | --- |
| DNS | `uav.caipiischenpi.top` 托管在 Cloudflare。**当前是代理模式（橙色云）**，所以访客解析到的是 CF 的地址、不是 `117.72.38.57`；换成仅 DNS（灰色云）才是直连源站，那样 443 就完全裸奔 |
| 端口 | 云安全组 + 面板「安全」页 + 系统 firewalld，**三道门**都要放行 `443`、`7000`（`80` 仅签证书时） |
| 443 的来源 | 代理模式下应**只放行 Cloudflare 的 IP 段**（CF 官方列表），否则任何人可绕过 CF 直连源站 IP，届时 3.3 里按 `CF-Connecting-IP` 计的限流就能被伪造绕过。实测从本机直连 `https://117.72.38.57/` 无响应（连接失败），说明目前源站 443 并未对全网开放——这一条是对的，改防火墙时别把它放开 |
| 服务器公网带宽 | ≥ 5 Mbps 或改按流量计费；热图 PNG 与首屏 JS 走这里 |
| frp 版本 | 0.71.0 已验证；使用 **TOML** 语法（0.3x 的 `[common]` ini 写法已废弃，照抄必启动失败） |
| 本机后端 | `config.json` 的 host 为 `0.0.0.0`、port `9090` |

`7000` 若本机是固定出口 IP，只在安全组里放行该 IP；家宽动态 IP 则全网放行并依赖强 token。

## 服务器侧

### 1. frps

配置副本在仓库 `frp/frps.toml`（该目录已 gitignore，token 不在版本库里），scp 到 `/etc/frp/frps.toml`。
改两处即可用：`auth.token` 与本机 `frp/frpc.toml` 保持逐字一致，`webServer.password` 换成自己的口令。

关键字段：

```toml
bindAddr = "0.0.0.0"
bindPort = 7000
proxyBindAddr = "127.0.0.1"      # 12002 只在回环监听，公网即使误放行也连不进来
```

`/etc/systemd/system/frps.service`：

```ini
[Unit]
Description=frp server
After=network-online.target

[Service]
ExecStart=/usr/bin/frps -c /etc/frp/frps.toml
Restart=always
RestartSec=3
LimitNOFILE=65535

[Install]
WantedBy=multi-user.target
```

```bash
mkdir -p /var/log/frps
systemctl daemon-reload && systemctl enable --now frps
systemctl status frps --no-pager     # 确认 active (running)
```

`frpc → frps` 这段 frp 默认已走 TLS，无需额外配置加密。

### 2. 证书

按你既有的二级域名证书流程处理即可。若走 Cloudflare，源站这张证书只用于 `CF → 源站` 那一段；
只要加密模式选 `Full (strict)`，就必须保证源站证书有效且未被 Cloudflare 的根证书替代。

### 3. OpenResty 反代（二级域名 + 面板管理）

#### 3.0 鉴权：当前有意不启用

现在整站匿名可用——`/` 与 `/api/*` 不给任何凭据就返回 200。这是**已知并被接受的取舍**，代价要说清楚：

- `/api/assess/report` 每次调用都消耗真实的 AI API Key，任何人都能触发；
- `/api/route/plan` 是单 worker 串行，任何人都能把本机 CPU 排队排满（包括你自己的开发）；
- 于是**唯一剩下的闸门是限流**，而它目前观测不到生效（见上方状态表与 3.3）。

若将来要加，最小改动是在 `rewrite/*.conf` 里补两行 + 建口令文件：

```nginx
auth_basic "UAV Planner";
auth_basic_user_file /www/server/panel/vhost/passwd/uav.htpasswd;
```

必须**整站**加，只加在 `/api` 上浏览器不会弹窗（`fetch` 不触发 Basic Auth 交互）。加了之后
`/.well-known/acme-challenge/` 会被一起挡掉，签发期间要临时放行。

#### 3.1 必修的一坑：压掉面板自带的静态正则

宝塔新建站点后，模板里带两条**没有 `proxy_pass` 的正则 location**：

```nginx
location ~ .*\.(gif|jpg|jpeg|png|bmp|swf)$ { expires 30d; }
location ~ .*\.(js|css)?$                  { expires 12h; }
```

nginx 的正则 location 优先于普通前缀 location。我们的 SPA 资源是 `/assets/index-<hash>.js`，
会命中第二条 → 面板跑去站点 `root` 目录找这个文件 → **404 白屏**，且日志看不出是被劫持的。

解法：反代这组规则里必须有一条 **`location ^~ /`**。前缀匹配带 `^~` 时，nginx 命中后**不再尝试任何正则**。
只写 `location /` 挡不住。

#### 3.2 站点、注入点与规则

1. 面板新建站点 `uav.caipiischenpi.top`，类型选**纯静态**（不要 PHP，免得再多一条 `\.php$` 规则）。
2. 规则写进 `/www/server/panel/vhost/rewrite/uav.caipiischenpi.top.conf`。
   该文件被站点 conf 在 `server{}` 内 include，且**面板不会重写它**；直接改站点那个 `xxx.conf` 的话，
   在面板里点一次 SSL 或反向代理就会被覆盖回去。

口令文件（只有下面的 `/frp-stats` 需要；不加这段就可以整个跳过）：

```bash
mkdir -p /www/server/panel/vhost/passwd
printf 'uav:$(openssl passwd -apr1)\n' > /www/server/panel/vhost/passwd/uav.htpasswd
```

`rewrite/uav.caipiischenpi.top.conf` 内容：

```nginx
client_max_body_size 8m;

proxy_set_header Host $host;
proxy_set_header X-Real-IP $remote_addr;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;

# ① AI 报告是 SSE：漏掉 proxy_buffering off 会表现为「一动不动、结束时整段吐出」
location = /api/assess/report {
    proxy_pass http://127.0.0.1:12002;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_buffering off;
    proxy_cache off;
    gzip off;
    chunked_transfer_encoding on;
    proxy_read_timeout 1800s;
    proxy_send_timeout 1800s;
}

# ② 气象热图 PNG：逐次现算，但历史数据集下入参确定即结果确定，适合长缓存。已实测 X-Cache: MISS → HIT
#    后端已回 `Cache-Control: public, max-age=<config.json 的 overlay.cache_seconds>`，前端包围框量化后 URL 才稳定。
#    寿命以回源的 max-age 为准（实测设 3600 时一小时就 X-Cache: EXPIRED），`proxy_cache_valid 200 7d` 只是兜底。
#    注意缓存键不含画质档位：改了 config.json 的 overlay 段要清一次 proxy_cache，否则 TTL 内仍吐旧图。
#    （proxy_cache uav 依赖 3.3 的 http 块声明；不想动 http 块就先删掉这三行 cache）
location ^~ /api/weather/overlay {
    proxy_pass http://127.0.0.1:12002;
    proxy_read_timeout 300s;
    proxy_cache uav;
    proxy_cache_key "$request_uri";
    proxy_cache_valid 200 7d;
    proxy_cache_lock on;
    proxy_cache_use_stale error timeout updating http_502 http_503;
    add_header X-Cache $upstream_cache_status;
}

# ③ 兜住其余一切。^~ 是这条存在的意义，见 3.1
#    缓存只能挂在 ② 那种具体接口上，**不要**在这里加 proxy_cache：`/` 与 `/index.html` 也是可缓存的
#    GET，重建 dist 之后用户仍会拿到缓存里那份旧 index.html，而它引的旧 hash 文件名已经不存在 → 白屏。
location ^~ / {
    proxy_pass http://127.0.0.1:12002;
    proxy_read_timeout 600s;      # 默认 60s 会让长寻路表现为「前端断连、后端日志正常」
    proxy_send_timeout 600s;
}

# frps dashboard（只监听 127.0.0.1:7500，这里加口令透出；不需要可整段删）
location ^~ /frp-stats {
    auth_basic "frps";
    auth_basic_user_file /www/server/panel/vhost/passwd/uav.htpasswd;
    proxy_pass http://127.0.0.1:7500/;
}
```

```bash
/www/server/nginx/sbin/nginx -t && /etc/init.d/nginx reload
```

#### 3.3 http 块指令（`proxy_cache` 依赖它，不是可选项）

`proxy_cache_path` 与 `limit_req_zone` 只能写在 `http{}`。面板升级/重编译 Nginx 会重写 `nginx.conf`，
所以把内容放进独立文件、只在 `http{}` 里加一行 include，并记住升级后复查：

```nginx
# /www/server/nginx/conf/uav_extra.conf
proxy_cache_path /www/server/nginx/proxy_cache_uav keys_zone=uav:20m max_size=2g inactive=7d use_temp_path=off;

# 访客全经 Cloudflare 进来，$binary_remote_addr 是 CF 的出口 IP：拿它做键等于把全世界当同一个访客，
# 要么一起掐死要么形同虚设。按 CF 回源头里的真实访客 IP 计。
limit_req_zone $http_cf_connecting_ip zone=uav_req:10m rate=4r/s;
```

```nginx
# nginx.conf 的 http{} 内
include /www/server/nginx/conf/uav_extra.conf;
```

然后在 `^~ /` 里加 `limit_req zone=uav_req burst=20 nodelay;`，overlay 里用 `burst=8`。

`$http_cf_connecting_ip` 是客户端可自带头，直连源站公网 IP 的请求能伪造它。所以这道限流的前提是
**443 只接受来自 Cloudflare IP 段的回源**（CF 官方段列表放进面板/防火墙白名单）；做不到就把限流当参考值，
别指望它是安全边界——尤其现在整站没有鉴权。

生效判定：`limit_req` 命中时返回 503，`X-Cache` 缺失且本机日志无该请求则说明缓存路径也没走到。

#### 3.4 反代目标写 `127.0.0.1` 还是 `IP:12002`

两者不能混：**12002 默认只在回环监听**（`proxyBindAddr = "127.0.0.1"`），此时写
`proxy_pass http://117.72.38.57:12002` 必然连不上；而且云主机的公网 IP 通常是 NAT 分配的、
并不在网卡上，从机器内部访问自己的公网 IP 本身也可能失败。

| OpenResty 跑法 | `proxy_pass` 写什么 | `frps` 的 `proxyBindAddr` |
| --- | --- | --- |
| 宿主机直装（宝塔常见） | `http://127.0.0.1:12002` | `127.0.0.1`（保持默认） |
| 容器但用 host 网络 | `http://127.0.0.1:12002` | `127.0.0.1` |
| 容器且 bridge 网络（1Panel 默认） | `http://<宿主 docker0 网关>:12002`，一般 `172.17.0.1` | 改成该网关地址，或 `0.0.0.0` 并在防火墙上只放行 docker 网段 |

判定命令（本机 `frpc` 连上之后执行）：

```bash
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:12002/api/meta/cities   # 宿主机上应为 200
docker exec <openresty容器> sh -c "curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:12002/api/meta/cities"
# 容器内返回 000 → bridge 网络，按上表第三行走
```

## 本机侧

配置已写好并通过 `frpc.exe verify` 校验：`frp/frpc.toml`（`serverAddr = 117.72.38.57`、
`localPort = 9090`、`remotePort = 12002`、token 已生成）。**不要**照抄它的旧示例值——
出厂示例里 `localPort = 22`，那是在转发本机的 SSH。

### 1. 一键起（演示 / 临时对外）

```bat
start.bat public
```

它在平时那套（后端 9090 + Vite 5173）之外多做三件事：

- 若 `frontend\dist` 不存在，**先同步跑一次 `npm run build`** 再起后端——挂载是在 import 时判断的，
  缺 dist 会让公网首页一直 404，直到后端重启；
- 后台跑 `npm run build:watch`，让 dist 跟着源码更新；
- 后台跑 `frpc`，日志在 `%TEMP%\uav_frpc.log`。

关闭那个黑窗口会连同隧道一起停掉（`scripts/start_watcher.ps1` 按 PID 文件收进程树）。
不带 `public` 参数时，任何端口都不对外。

### 2. 手工分别起

```bat
cd frontend && npm run build:watch          REM 另一个窗口
G:\uav-planner-enhance\frp\frpc.exe -c frpc.toml    REM 工作目录需在 frp\ 下，或写全路径
```

`frpc` 输出里看到 `login to server success` 与 `start proxy success` 才算成。

### 3. 常驻（长期公开走这条）

`start.bat` 是给人双击的，公网服务不能依赖它。用 NSSM 注册成服务（不依赖是否登录）：

```bat
nssm install frpc "G:\uav-planner-enhance\frp\frpc.exe" "-c G:\uav-planner-enhance\frp\frpc.toml"
```

后端同理需要常驻方式（`start.bat`，或把 `python -m uvicorn main:app --host 0.0.0.0 --port 9090` 注册成服务；
长跑时去掉 `--reload`）。电源计划必须设为不睡眠——合盖/睡眠是公网掉线的第一大原因。

## 验证顺序（别跳步）

1. 本机 `curl http://127.0.0.1:9090/api/meta/cities` → 后端活着。
2. `npm run build` 通过后 `curl http://127.0.0.1:9090/` → 返回 `index.html`（确认挂载生效）。
3. 服务器 `curl http://127.0.0.1:12002/api/meta/cities` → **隧道通**。失败只查三处：7000 是否放行、
   两边 token 是否一致、`journalctl -u frps`。与 OpenResty 无关。
4. `curl -I https://uav.caipiischenpi.top/` → 当前形态下 **200 是正确结果**（整站无鉴权；若你按 3.0 加了口令，这里才应是 401）。
   响应头里出现 `Server: cloudflare` 说明流量确实绕了 CF。
5. 同一 URI 连打两次 `/api/weather/overlay` → 第一次 `X-Cache: MISS`、第二次 `HIT`；`HIT` 时本机后端日志
   **不应**出现该请求，这才证明它没过来。
6. 浏览器走完一轮功能，重点看 AI 报告的 `delta` 是否逐条到达（验证 SSE 未被缓冲）。
7. 手工停掉本机 `frpc`，确认公网返回 502 而不是白屏。

## 故障对照

| 现象 | 大概率原因 |
| --- | --- |
| 页面白屏、`/assets/*.js` 返回 404 | 面板自带的 `location ~ .*\.(js\|css)?$` 劫持了请求，缺 `location ^~ /`（见 3.1） |
| 别人打开页面但所有接口失败 | `API_BASE` 又被写死成 `localhost`（应为空串走同源） |
| AI 报告卡住后整段吐出 | 该 location 漏了 `proxy_buffering off` |
| 长寻路莫名断连，后端日志却显示跑完 | `proxy_read_timeout` 仍是默认 60s |
| 服务器 `curl 12002` 拒绝连接 | frpc 未启动 / token 不匹配 / 7000 未放行（三道门之一） |
| `curl 12002` 通但公网 502 | `proxyBindAddr` 与 `proxy_pass` 的地址或端口不一致（见 3.4） |
| 公网能读到 `.py` 源码 | 有人把 dev server 端口加进了 `[[proxies]]`，立即删掉 |
| 改了前端但用户仍看旧版或直接白屏 | 兜底 `^~ /` 上挂了 `proxy_cache`（见 3.2 ③），或 CF 边缘缓存了 HTML |
| 一部分人随机 503、且与个人操作频率无关 | `limit_req_zone` 仍以 `$binary_remote_addr` 为键，全体访客共用一个桶（见 3.3） |
| 热图 `X-Cache: HIT` 却仍要两秒 | 本机已经不参与了，剩下的是 CF↔源站的跨洋传输 |

## 已知限制

- **本机是单点**：关机、睡眠、断网、Windows Update 都会让服务下线。
- **并发有限，但原因不是「数据占内存」**。实测后端进程 RSS 只有 0.2 GB（NetCDF 从不整体载入，16 GB 内存也装不下 614 GB）。真实限制是三条叠在一起：单 worker 串行、一次取网格有约 0.19 s 花在 dask 图优化上、数据盘是 USB 外置机械盘。多人同时点「规划」会互相排队，靠 `limit_req` 也只是排队。
- **AI 配额与 CPU 都无屏障**：当前整站不鉴权，`/api/assess/report` 消耗真实 API Key、`/api/route/plan` 打满本机 CPU，任何人都能匿名触发；理论上唯一的闸门是限流，而它尚未确认生效（见 3.0、3.3）。
- **GPU 加速帮不上**：4D A* 是串行搜索，可优化的都在取数与单核 CPU 侧（详见 `AGENTS.md` 的 Performance Facts）。
- 首屏 JS 实测 1.46 MB（gzip 后约 484 KB），走服务器公网带宽；访问者一多就要考虑代码分包或提高带宽档位。
