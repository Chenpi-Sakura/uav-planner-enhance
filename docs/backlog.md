## B1 · 多方案航线与优先级选择

### 会议诉求

> "路径规划的时候可以出一条线。现在分紧急常规经济的话，你可以是多条线，然后让他给你做一个选择，
> 或者说是用户自己来选择。但是这几条线你要出线，比如说你拿实线，旁边一条线可以拿虚线出现。"

### 现状与证据

`priority` **不进入寻路**，只在功能一里当绕行比阈值用：

- `backend/feasibility.py:62-63` → `settings.DETOUR_RATIO_LIMIT.get(priority, ...)`
- `backend/config.py:85-89` → urgent 1.25 / normal 1.5 / economy 2.0
- 调用链上 `plan_path_ex(...)` 收到的参数里没有 priority，A* 的硬阈值与软惩罚也不看它

结果：三种优先级跑的是**同一条几何路径**，只有"结论 / 绕行是否超阈 / 文案"会变。

前端另有一处独立原因放大了"没反应"的观感：

- `frontend/src/components/FeasibilityPanel.vue:11` 点击只写 `store.priority`，**没有 watcher 重新发请求**；
- 必须再点一次「开始评估」（`:320` 才把 priority 放进请求体）。

地图侧 `dashArray` 现有用法（`MapContainer.vue:291`）是"无分段风险数据时的单条回退线"，不是多方案对比图层。

### 待决策

优先级分档要改变的是**搜索代价**还是只是**结论阈值**？若要出三条不同的线，建议口径：

| 方案 | 距离偏好 | 湍流容忍 | 备注 |
| --- | --- | --- | --- |
| 经济 | 最短距离 | 只躲硬阈值（现有软惩罚减弱） | 直线方向占比高 |
| 常规 | 现状不变 | 现状软惩罚 | 保持已有验收结果 |
| 紧急 | 最小风险（允许绕远） | 软惩罚加重、可收紧硬阈值 | 与"紧急=最快"直觉相反，需确认语义 |

**注意语义冲突**：会议把"紧急"理解成什么，直接决定实现方向——紧急是"最赶时间（要短）"还是"最要紧的任务（要稳）"？当前阈值口径（紧急最多 +25% 时间、经济最多 +100%）取的是前者：紧急**不容许**绕行。若按上表实现紧急=最小风险，与现有 `DETOUR_RATIO_LIMIT` 的方向正好相反，两者必须挑一个。

### 代价

3 次规划 ≈ 单次 1.6s → 约 5s（不含取数复用）。需新增：方案列表状态、地图多 polyline 图层、实线/虚线样式、方案切换时的结果面板联动。验收矩阵要重跑。

## B2 · 时间窗口：日期标注与扫描粒度

### 会议诉求

> "它没有显示哪一天的哪一个时间续飞……光显示时间了，而且这个时间应该是以 3 小时为单位。"
> "因为我们当时的数据，它的分辨率就是 3 小时。"

### 现状与证据

**(a) 日期丢失 —— 确认是缺陷，纯前端展示层。**

后端 `recommended.takeoff` / `landing` 返回完整 ISO 日期时刻（`2022-07-01T07:00`，
`backend/time_window.py:499-501`），前端在 computed 里把它砍掉了：

```
frontend/src/components/TimeWindowPanel.vue:226-229   takeoffTime = t.split('T')[1]
frontend/src/components/TimeWindowPanel.vue:230-233  landingTime = t.split('T')[1]
```

推荐卡标题「推荐起飞 07:00」因此不带日期。备用时段表与 7 天推演列表里 `date` 字段是有的
（`:162`），只有推荐卡缺。**修法是展示层加日期，不需要动后端。**

跨日窗口需要单独定口径：降落时刻可能落在次日，`window: [起, 止]` 目前只存 `HH:MM`
（`time_window.py:500`），跨午夜时"23:30 → 01:10"会被读成回退，展示层要能标注「+1 天」。

**(b) 「数据是 3 小时分辨率」这个前提，本机实测不成立。**

读 `data/tibet_2022_upper_u.nc`：

```
time frames: 8760
step histogram: {1: 8759}          # 相邻帧间隔全为 1 小时
sizes: {'time': 8760, 'lev': 19, 'lat': 303, 'lon': 543}
```

进一步验证逐小时帧**不是**用 3 小时真值线性内插造的（500hPa 整层 162,970 个有效点）：

| 检验 | 结果 | 若为线性内插 |
| --- | --- | --- |
| `max|u₁₂₁ − (u₁₂₀+u₁₂₂)/2| / max|u|` | 34.96% | ≈0 |
| `max|u₁₂₂ − (u₁₂₁+u₁₂₃)/2| / max|u|` | 36.05% | ≈0 |
| 相邻帧最大差 | 11.3 m/s | 很小 |

即逐小时数据有独立信息量，1 小时扫描不是在做无用功。这一点与
`docs/决策平台实现计划.md` §5.3 的记载一致，与会议记忆冲突。

**但会议诉求与实测结论不矛盾**：粒度本来就是可配的，`backend/config.py:97-98`
`TW_SCAN_STEP_HOURS: int = 1`，改成 3 即得 8 个 3 小时槽位（`TW_MAX_SCAN_SLOTS=48` 不会限制它）。

### 待决策

老师要的是哪一个？

1. **界面按 3 小时标注/展示**（时段表每 3 小时一行，曲线刻度 3h）—— 建议保留 `TW_SCAN_STEP_HOURS=1` 的扫描精度，只做展示层聚合；
2. **扫描本身降到 3 小时** —— 一个配置项的事，但会丢掉日内精细窗口，答辩时"为什么不用逐小时数据"要能答；
3. 两者都要 —— 扫描 1h、对外按 3h 归并出推荐窗口。

在 (1)/(3) 下还需确认：日期标注的格式（`07-01 07:00` 还是 `7月1日 07:00`）。

## B5 · 湍流参数化用了平均量而非脉动量

### 会议结论（本次核对中确认为**真实缺陷**，且影响面最大）

> "计算湍流的时候不是需要一个脉动量，然后我们这个里面用的是一直是平均量，直接拿平均量。
> 真的脉动量是拿真实数据减去它的平均数据……但是我们用的直接就是直接用的那个点的数据。"
> "申报书里写的公式是对的，但是我们用的是不对的。"

### 现状与证据

`backend/meteorology.py:10-16`：

```python
wind_speed_sq = u**2 + v**2 + w**2
tke = 0.01 * 0.5 * wind_speed_sq        # 原始风场，未扣任何均值
```

同一公式在 `data_loader.py` 另有两处内联复制，三处必须一起改否则结论与出图会互相矛盾：

| 位置 | 用途 |
| --- | --- |
| `backend/data_loader.py:74-75` | 单点查询，走 `calculate_tke/edr` |
| `backend/data_loader.py:132-133` | 矢量化网格查询（规划器/评估实际吃的就是这个） |
| `backend/data_loader.py:422-423` | overlay 出图（tke / edr 图层） |

docstring 自己写着 "This is a simplified parameterization placeholder"，即该实现从一开始就是占位版。

### 影响

TKE 与**平均风速同向**，后果是系统性的：

- 高原急流轴（平均风 30–40 m/s）被当成全域最强湍流区，A* 硬阈值 `TKE≥1.0` 大面积命中；
- 真实湍流高发区（风切变、地形波、午后对流）因平均风不大而被压低甚至漏判。

因为 TKE/EDR 是 A* 的硬约束输入、也是时间窗口每个槽位的判据，这条**直接决定所有
「可飞/不可飞」结论与推荐起飞时刻**，不是"颜色好不好看"的问题。方向上：
急流季偏保守（误判不可飞偏多），午后热对流偏乐观（漏判）。

与会议另一处判断的呼应：会上怀疑"刚出现那几条线算的有问题可能跟这个有关系，也可能跟算法有关系"
——见 A4，算法侧核心代价函数零改动，所以这个怀疑方向是成立的。

### 候选改法

`u' = u − ū`（v、w 同理）后再取 `0.5·(u'²+v'²+w'²)`。要拍板的是 ū 的口径：

| 方案 | ū 定义 | 产出 | 成本 |
| --- | --- | --- | --- |
| 轻量 | 该层该格点的**全年均值**（年均值场） | 单个小 NC（303×543×19×6 变量，几十 MB 量级） | 一次全量顺序扫（614GB / USB 机械盘），代码改动小 |
| 中间 | 按**月份 × 层 × 格点**均值 | 12 份年均值场 | 同上，多一层分组 |
| 完整 | 月 × 日序（或滑动窗）均值，分离日变化信号 | 数百份切片 | 存储与扫盘次数显著上升 |

轻量版即可压掉急流轴上的绝大部分假高值。建议先做轻量版，量一遍结论翻转比例再决定是否加深。

### 连带工作

1. 三处公式收敛成 `meteorology` 单一入口（否则出图与寻路会用到不同 TKE）；
2. 阈值 0.4 / 0.7 / 1.0（TKE）、0.1 / 0.2 / 0.3（EDR）是按"原始风速量级"标定的经验系数
   （`meteorology.py:12-15` 注释：10 m/s → 0.5 中度、15 m/s → 1.125 危险）。改成脉动量后
   数值量级会整体下降一个台阶，**阈值必须重新标定**，否则全部用例变成"到处可飞"；
3. M5 验收矩阵（`docs/决策平台M5-联调验收记录.md` §3）与 `golden_plan.py` 的金标基线都要重生成。

## B6 · 限制区与地形跟随：当前代码里没有

### 会议诉求

> "我们这个考虑限制区是不是有点那个，我感觉青藏高原真的能这么大一个军区吗？"
> "地形跟随逻辑跟实际海拔……这个应该也不太需要考虑，这个是平原，天津地区还好。"

### 现状与证据

- 全仓库（`backend/` + `frontend/src/`）搜 `限制区|禁飞|restricted|军事|管制|机场|缓冲区` **零命中**；
- `backend/planner.py` 搜 `elevation|srtm|terrain|海拔|地形` **零命中**：规划器没有任何地形跟随或高程惩罚项，
  唯一与地形沾边的处理是「数据缺失即 NaN → 当作不可飞格点跳过」（`planner.py:347-348`）；
- SRTM 高程只被 `data_loader.py` 读，用于剖面与出图，不进搜索。

因此 `docs/决策平台实现计划.md` §2.1（`:33`）写的"软惩罚（中度湍流、**坡度、高海拔**）"**与代码不符，属过期描述**，需要修正该文档。

会议中提到的"风速 >15 m/s 代替缓冲区 / 通信限制区 / 机场距离"是**参考论文（徐晨，2019，
《地理信息科学》）的建模口径**，不是本系统已有的实现。本系统的障碍物只有湍流硬阈值与数据缺失两类。

### 待决策

要不要接？接的话先解决数据来源：

| 缺口 | 说明 |
| --- | --- |
| 限制区几何 | 当前 NetCDF 数据集里没有任何空域信息，需要外部矢量数据（禁区/限制区/航路网）及其坐标系与生效时段口径 |
| 地形约束 | 若要做"地形跟随"，需先明确是**最低安全高度**（离地间隙）还是**垭口走廊**；前者要 SRTM 进 A\*（当前无），后者要航路网数据 |
| 平原/高原差异 | 会议点到的这个问题，前提是地形项存在；当前实现里不存在，讨论应转为"是否新增" |

建议：本轮不排期，先修正计划书 §2.1 的过期描述，并在答辩口径里明确"当前障碍物模型 = 湍流 + 数据覆盖"，
避免被追问限制区时给不出答案。

## A4 · 核心寻路算法是否被功能扩展改动（**已核查完毕**）

会议记录：

> "我问他算法有没有发生变化，他说没有。就很奇怪……我怕他把核心的这个路线算法怎么改了。"
> "没有，其实改了，告诉你，别改了。不知道无法判断。"

**结论：A\* 的代价函数与启发式零改动；改的是"失败时说什么"和"用哪个时刻的气象"。**
时间对齐后，同一份数据上 9/11 用例的航线路径逐比特一致。

完整证据、A/B 对跑数据、变更清单与复现命令见 `docs/决策平台A4-算法一致性核查.md`。
其中与本文件其他条目相关的两条：

- 会议看到的"线变短/消失"，主因是**删掉了"搜不到就返回直线"的兜底**与新增的起点安全校验（不是算错了）；
- B5 的脉动量修正一旦落地，本核查的全部数字作废，需重跑。
